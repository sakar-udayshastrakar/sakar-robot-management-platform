# Keenon → Sakar Architecture Comparison

A side-by-side comparison only — **no ranking or scoring is implied by row order or by which column
has more entries.** "Sakar Target" describes a proposed direction already recorded in Phase 3's
`SAKAR_APPLICATION_BOUNDARIES.md`; it is not an implementation commitment or timeline.

| Layer | KEENON | SAKAR CURRENT | SAKAR TARGET |
|---|---|---|---|
| **Application layer** | 5 separate APKs: `com.keenon.peanut.clean` (operator + Super User + Debug), `com.keenon.peanut.peanutservice` (Installation Assistant), `com.keenon.systemservice` (shared MQTT/TTS/Voice), `com.keenon.krlog` (log utility), `com.keenon.remote_control_oray` (remote support) | 1 application: `SakarC40Agent` (`com.sakarrobotics.c40agent`), covering the operator/Super User/Debug scope only | Proposed: keep `SakarC40Agent` as the operator/Super User/Debug app (matches Keenon's own precedent); add separate `sakar-installation-assistant` and `sakar-log-utility` apps later; reserve `sakar-service` and `sakar-remote-assistant` until needed/licensed |
| **SDK** | Their own applications call their own SDK/internal protocols directly and without restriction (e.g. unrestricted `MotorComponent.enable()`, direct `Mapping.db` access, direct rosbridge access) | Licensed, third-party `peanut-sdk-release.aar` only — a single module (`sdk`) is the only code allowed to import `com.keenon.*`; every other module goes through `domain`/`data` abstractions | Same licensed SDK boundary retained; no plan to bypass it or access Keenon's internal protocols without explicit permission |
| **Robot control** | Full SDK + internal protocol access (motor, navigation, motion-board SCM-IoT protocol, all with no per-app authorization observed) | Real SDK calls gated by `OperatingMode` (`DIAGNOSTIC_ONLY` default, `HARDWARE_TEST` never set anywhere in the codebase) | Same gating model retained; `HARDWARE_TEST` remains an explicit, documented, never-auto-enabled seam for a future supervised session |
| **Mapping** | Live SLAM build/edit/save/multi-floor/virtual-wall/elevator/gate, backed by a rich local `Mapping.db` and a rosbridge connection to a separate SLAM computer | Map screens exist in the UI (`maps/*`) but are `UNAVAILABLE`/local-canvas-only — real map *read* where the SDK supports it, real local zone-drawing, **no SLAM engine invented** | Per Phase 4 feasibility analysis: file-level map management (list/download/rename/delete via the public SDK) is the lowest-risk next step; live map-building remains blocked pending physical-robot/licensing resolution |
| **SLAM** | Runs on a separate, non-Android compute node (existence `PHYSICAL-HARDWARE CONFIRMED`; role/protocol `STATIC-ANALYSIS CONFIRMED`), reached via an undocumented internal rosbridge/WebSocket protocol | None — no SLAM engine, mock, or fake data exists anywhere in `SakarC40Agent` | Not implemented until the physical-robot audit (`07_NEXT_PHYSICAL_ROBOT_AUDIT.md`) and a licensing/access decision resolve whether Keenon's own SLAM computer can be reused |
| **Cleaning** | Real `CleanComponent`-backed brush/pump/fan/water/workstation control (internal to Keenon's own apps; not present in the licensed public SDK at all) | `Capability.SIMULATED` — time-based session simulation only; `Capability.UNAVAILABLE` for any actual cleaning hardware, since `CleanComponent` is confirmed absent from the licensed AAR | Unchanged unless/until a different SDK tier exposing `CleanComponent` becomes available — no plan currently exists to fabricate this |
| **Scheduling** | `TimerTaskActivity` + related task-config activities inside `peanut-clean`, backed by their own cloud API (`PeanutApi`, `/api/cleanapp/iot/...`) | `Capability.LOCAL` — Room-backed (`ScheduleRepository`), no cloud, no robot hardware involved | Unchanged; no cloud-sync requirement identified for Sakar's scheduling feature |
| **Cloud** | Multiple, purpose-separated cloud surfaces: `PeanutApi` (cleaning-app cloud sync), `HttpElevatorApi` (elevator-vendor IoT), region-specific map-backup consoles (`console.peanut.keenonrobot.com`-style), TTS/Voice cloud (Microsoft Cognitive Services + iFlytek), Oray/Sunlogin remote-support backend | None of the above — `SakarC40Agent`'s own `:api` module implements a separate, Sakar-authored MQTT integration (`AgentMqttClient`) to a Sakar-controlled backend, architecturally unrelated to any Keenon cloud service | Continue building Sakar's own backend integration (`:api` module) independently; no plan to call any Keenon-owned cloud endpoint |
| **Telemetry** | `PeanutRuntime.getRuntimeInfo()` and a 65-topic pub/sub surface, consumed internally by their own apps | `telemetry` module (`RuntimeSnapshot`, `HealthEvent`, `ConnectionStatus`, `RawSnapshot`) sourced from the same licensed SDK, forwarded via `:api`'s MQTT telemetry publisher to Sakar's own backend | Unchanged in direction; continues to be sourced from the same licensed SDK surface only |
| **Logs** | Separate, standalone, boot-autostarted `com.keenon.krlog` APK with device-wide (`READ_LOGS`) log capture | In-app `Capability.REAL` log viewer (`SdkCallLogger`, max 500 entries, Sakar's own SDK-call log only — no device-wide log access) inside `SakarC40Agent`, reached from Super User | Proposed: a separate `sakar-log-utility` app mirroring krlog's broader, device-wide scope, alongside (not necessarily replacing) the existing narrower in-app SDK-call log — an open decision, not yet resolved |
| **Remote support** | Separate `com.keenon.remote_control_oray` APK, built on a licensed third-party Oray/Sunlogin SDK | None | Reserved (`sakar-remote-assistant`) — explicitly licensing-gated; requires acquiring an equivalent third-party remote-access SDK before any implementation is possible |
| **Installation** | Separate `com.keenon.peanut.peanutservice` APK, a Chromium WebView shell hosting a bundled web SPA, itself talking to the separate SLAM computer for the actual mapping/commissioning work | In-app `installation/*` screens inside `SakarC40Agent`, mostly `Capability.UNAVAILABLE`, real Factory Reset (clears local data only) | Proposed: a separate `sakar-installation-assistant` app, matching Keenon's own packaging separation — an open architectural question already flagged (`SAKAR_APPLICATION_BOUNDARIES.md`) since today's in-app screens don't yet reflect this proposed separation |
| **Hardware** | RK3288 UIB board (Android/application computer, `PHYSICAL-HARDWARE CONFIRMED` board markings) + a separate SLAM computer (`PHYSICAL-HARDWARE CONFIRMED` to exist) + a separate motor/motion controller board (`STATIC-ANALYSIS CONFIRMED` via the SDK's own SCM-IoT protocol) | Runs on whatever Android hardware the CleanBot5000Plus tablet provides today (assumed to be the same RK3288 UIB, not independently re-verified by Sakar) | `ROCK 4D` is under investigation as a possible RK3288 replacement — **explicitly not approved**; no interface investigation has been performed (see `01` §26, `03`) |

**Reminder, restated from the task's own instruction:** this table is descriptive, not a decision
document. No cell above authorizes any implementation work.

**Cross-reference note:** a separate audit of Keenon's official, customer-facing C40 documentation
([`09_KEENON_OFFICIAL_C40_DOCUMENTATION_AUDIT.md`](09_KEENON_OFFICIAL_C40_DOCUMENTATION_AUDIT.md))
found nothing that changes any cell in the table above. Official documentation confirms LiDAR's
existence/purpose and a "Binocular Stereo Vision" sensor (refining the "Mapping"/"SLAM" rows'
sensor picture slightly — see `09` §7 row 3) and gives new operational specs (map-area limit,
passability specs, a two-layer map model), but says nothing about application separation, SDK
boundaries, cloud architecture, or any of the other rows in this comparison — those remain sourced
entirely from the APK-based Phase 3/4 work as before.
