### Robot Online/Offline Status Consistency

**Nineteenth pass, backend + frontend slice (branch `dev`, on top of `08b20ac`, working tree — not yet committed):** fixes a real status contradiction in the UI — the Robots page could show **Connection: ONLINE** for a robot whose Alerts page simultaneously showed an open *"No heartbeat or telemetry received within the configured offline threshold"* alert.

### Map UI Display Fix

**Twenty-third pass, frontend-only slice (branch `dev`, on top of `a64766b`):** fixes the Robot Detail → Map tab rendering the floor-plan as a small drawing surrounded by large white space, reported against the real, live-synced Demo Piece map. - **New content-crop feature, presentation-only.** `utils/mapContentBounds.ts` adds `computeContentBounds()` (a pure, DOM-free RGBA bounding-box scan — a pixel counts as content when non-transparent and any channel is below a 250 "near-white" threshold) and `computeCropStyle()` (pure percentage math turning a bounding box + the image's natural size into a container `aspect-ratio` plus the `<img>`'s `width`/`left`/`top` as percentages). A new hook, `features/robots/useMapContentCrop.ts`, decodes the *same already-fetched* map image (no new network request) into an offscreen, never-DOM-attached canvas purely to read pixel data, adds 12px of padding around the detected bounds, and fails soft — returning null bounds (full uncropped fallback) rather than throwing — for jsdom, a tainted canvas, or a genuinely blank image. `RobotMapPanel.tsx` renders the cropped, percentage-positioned `<img>` when bounds are available and falls back to the original full-image layout otherwise, keeping the same `<img alt="Robot floor-plan map">` element in both paths.

- **Future overlay compatibility, documented not built:** the same bounds used for the visible crop give a reusable placement formula for a future source-image point `(px, py)` — `left% = (px - bounds.x) / bounds.width * 100`, `top% = (py - bounds.y) / bounds.height * 100` — spelled out in `mapContentBounds.ts`'s own comment. `bounds` is not yet threaded out to any overlay component as a prop; wiring that is left for when overlay work is actually scoped.

## Robot Integration Status

**Path 1 — current, live-tested, Keenon-dependent:**
```
Sakar Backend  →  Keenon Robot Adapter  →  Keenon Cloud (https://cloud.robotkeenon.com)  →  Robot
```
The `KeenonRobotAdapter` (`backend/src/main/java/com/sakarrobotics/cloud/integration/keenon/`) implements the live-tested read/control operations (status, battery, telemetry, areas, temporary task, pause, recharge) against Keenon's Open Platform, gated by the robot capability model so unsupported operations return `UNSUPPORTED_CAPABILITY` rather than being attempted. This path is **KEENON-CLOUD DEPENDENT** by design and is explicitly not the target architecture — see Master Requirements Part 10/40.

**Path 2 — target architecture, MQTT telemetry now implemented in software (Phase 3):**
```
SakarC40Agent  →  MQTT  →  Sakar Cloud  →  PostgreSQL  →  WebSocket
```
Presence/heartbeat/telemetry/events/errors flow agent → cloud → database over MQTT, with idempotent ingestion, robot/tenant identity verification, and real-time WebSocket publish — see `docs/architecture/SAKAR_MQTT_ARCHITECTURE.md`. **This is a software pipeline verified by automated tests only — no MQTT broker or physical robot was run against it in this session.** The `SakarRobotAdapter` (REST/adapter-based control path, distinct from this MQTT telemetry path) is still a stub — every method throws `FEATURE_NOT_YET_IMPLEMENTED`; lock/unlock is not implemented on either path.

**Phase 7 addition — non-lock command dispatch now flows both ways in software:** `SakarC40Agent` consumes its `commands` topic (`CommandDispatcher`) and reports RECEIVED/EXECUTING/COMPLETED/FAILED/TIMEOUT back over the EVENT channel; the backend's `CommandResultIngestionService` applies these to `RobotCommand`/`CommandResult`. `START_TASK` is executed by an explicitly-labeled software simulation (`SimulatedRobotCommandExecutor`) — the officially-distributed Peanut SDK AAR this agent bundles has no cleaning-control API to call for it (confirmed by decompilation — see the Current Phase note above and `ROBOT_AGENT_COMMAND_LOOP_INVESTIGATION_AND_DESIGN.md`). A `COMMAND_SUCCESS` status from this pipeline today means "the agent's software simulation finished," never "a robot cleaned anything." **`RETURN_TO_DOCK`, added in a second pass, is executed for real** — `PeanutSdkReturnToDockExecutor` calls the officially-distributed SDK's `BatteryComponent.autoCharge()`, gated by the same `OperatingMode.HARDWARE_TEST` guard as every other actuation method — but its terminal status is `COMMAND_DISPATCHED`, not `COMMAND_SUCCESS`, because SDK acceptance is not confirmed physical completion. **`GO_TO_POINT`, added in a third pass, is likewise executed for real** — `PeanutSdkGoToPointExecutor` calls the officially-distributed SDK's `NavigationComponent.setTarget(IDataCallback, int)` with a caller-supplied, pre-registered destination id (never invented by this project — both the agent and the backend reject a missing/negative one before the SDK or MQTT is touched), gated the same way, also reporting `COMMAND_DISPATCHED` rather than `COMMAND_SUCCESS`.

- Physical C40 validation: **NOT PERFORMED.** No physical robot has been connected to, or controlled by, any code in this repository.
- Remote lock/unlock: **NOT PHYSICALLY CERTIFIED, NOT IMPLEMENTED IN SOFTWARE EITHER.** No lock/unlock code exists in the backend, MQTT layer, or agent — the ten physical validation conditions in Master Requirements Part 11/38 remain entirely unaddressed. Do not represent lock/unlock as production-ready anywhere derived from this README.
- Keenon Cloud independence: **NOT ACHIEVED.** Path 1 still requires Keenon Cloud. Path 2 removes that dependency for telemetry, but has not been proven against a real robot.
