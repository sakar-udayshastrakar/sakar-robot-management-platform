# database/

**Status note (documentation sync, 2026-09-22):** this `database/` directory itself remains unused — it is not where the schema actually lives. The real Flyway migration set (`V1`–`V18`) lives under `backend/src/main/resources/db/migration/` and is applied automatically on backend startup; the schema described below is implemented, not "not yet implemented." This directory was reserved for database-side tooling separate from the backend's own Flyway setup, and nothing has been added to it — that specific reservation is still accurate, the broader claim below it no longer is.

Tables per `docs/architecture/SAKAR_ROBOT_PLATFORM_DATABASE.md` and now actually present in the schema: `organizations`, `sites`, `users`, `roles`, `permissions`, `robots`, `robot_models`, `robot_credentials`, `robot_status`, `robot_telemetry`, `robot_events`, `robot_errors`, `robot_alerts`, `robot_commands`, `command_results`, `robot_locks`, `robot_tasks`, `task_events`, `maps`, `map_points`, `cleaning_sessions`, `charging_sessions`, `notifications`, `audit_logs`, `application_logs` — plus several added after that original list (`keenon_area_mappings`, `keenon_cleaning_mode_mappings`, `keenon_back_point_mappings`, `keenon_robot_scene_configs`, `mqtt_inbound_messages`, `sakar_robot_serial_seq`, and others — see the migration filenames themselves for the full current set).

**Security note carried forward from `docs/security/SAKAR_SECURITY_REQUIREMENTS.md`:** the `audit_logs` table must be append-only at the database-role level (`INSERT`/`SELECT` only, no `UPDATE`/`DELETE` for the application role) — this is a schema/migration requirement, not an application-code convention. **As implemented today, this is not yet enforced at the database-role level** — immutability currently rests on application-code discipline only (no service ever issues an `UPDATE`/`DELETE` against `audit_logs`), not a `REVOKE`-based DB role restriction. This remains a real gap, not a resolved requirement.

**Known current data-integrity limitations** (see the root `README.md`'s Database row/Known Limitations for the full, current list): no telemetry/event retention, purge, or partitioning strategy exists (`robot_telemetry`/`robot_events` grow unbounded); `organizations.name` has no uniqueness constraint; `robots.external_robot_id`/`vendor_serial_number` are enforced at the application layer only, not by a DB unique constraint.
